## Реализация и проверки перед boot

Новый standalone код в `ports/ziyi-ios-sweet/s2/`, S1 не изменён.
112-byte BootShim и placement FD A7400000 / 3 MiB сохранены как в S1.
Payload передаётся отдельным Android ramdisk; source range читается из
ABL FDT и проверяется до dereference. Допустимы измеренный boot-staging
source window после kernel image и отдельное обычное low-DRAM window;
FD/stack/framebuffer/DTB overlap исключается. Copy targets только внутри
закреплённого high-RAM candidate. Полный pinned payload SHA обязателен.

Проверены nsegs, offsets, file/vm sizes, integer overflow, segment ordering,
destination limits, ADT и boot_args placement. Никаких UFS/USB/touch/PMIC
probes/reset/SMC в loader нет. Шесть hardware provider units ядра ранее
заменены no-I/O stubs; linked providers проверены отдельно в S2 CI audit.

На ПК реально выполнен тот же C loader в 128-MiB arena по VA 32 GiB,
с 64-KiB inaccessible guard regions. Полный arena hash совпал с Python
эталоном, включая незатронутые gaps. Восемь повреждённых payloads отклонены
без изменений arena. SHA-256 сверена с hashlib на четырёх inputs, включая
весь реальный payload. FDT valid/invalid cases и реальные relocated source
range/overlap cases проверены. Actual C optical writer прошёл 5 pages ×
4 JPEG/rotation cases, framebuffer guards и семь false-success cases.

## S2X и крупные точки

Образ S2X build3 использует тот же loader/payload и единственный audited
indirect call к `0x80148b488` с x0=`0x8020c4000`, после повторного optical
подтверждения. SHA образа:
`3c38cb5ab1494f50c8b85a146a611e0286101ec5c82420346e08c74b8b0574ac`.
Runner требует аппаратный S2P PASS с тем же kernel/BSS и boot_args/layout.
ADT-only правка может сузить console mapping; новая ADT всё равно полностью
проверяется по SHA на самом телефоне перед entry. Для S2X
камера пишет 180 s: измеренные ~73 s hashes + telemetry оставляют место
для собственного kernel output. Root disk отсутствует; `rd=md0` — только
намерение следующего RAM-root этапа, готового userspace ещё нет.
